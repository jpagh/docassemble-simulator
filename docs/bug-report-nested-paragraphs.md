# Bug report: published DOCX attachments contain nested `<w:p>` elements

Status: written for triage — not yet filed upstream or in the target package
tracker.

This report contains observations only. It deliberately does not speculate
about the cause or propose a fix.

## Summary

Strict OOXML validation of DOCX attachments generated by the Family workflow
reports paragraphs (`<w:p>`) nested inside other paragraphs in
`word/document.xml`. Tolerant readers open the files normally, so the issue
only appears under strict structural validation.

## Environment

| Component | Version |
| --- | --- |
| docassemble-simulator | 26.8.0 (commit `51a5e0b` and later) |
| Target package | `docassemble-automatedpleading` (branch `family-category`) |
| docassemble-base | 1.10.7 |
| docassemble-webapp | 1.10.7 |
| docxtpl | 0.20.2 |
| docxcompose | 2.2.0 |
| python-docx | 1.2.0 |
| Python (target interpreter) | 3.14.7 |

## Steps to reproduce

1. In the target workspace, complete the Family flow to the “Workflow
   Complete” screen (six non-PDF documents; the retained session can be
   replayed with `docassemble_simulator refresh`).
2. Inspect the JSON result's `attachments` array. Each entry carries a
   `structure` field (`"ok"`, `"warning"`, or `"n/a"`) and, for warnings, a
   `diagnostics` list whose entries name the offending part and the nested
   paragraph count.
3. Alternatively, run the structural check directly against a published
   attachment's local path.

The strict check counts, per WordprocessingML part in the package, every
occurrence of a `<w:p>` element that is a descendant of another `<w:p>`
element (namespace
`http://schemas.openxmlformats.org/wordprocessingml/2006/main`).

## Observed behavior

On the retained run, 7 of the 14 published DOCX attachments carried a
`structure` of `"warning"`:

| Published attachment | Part | Nested `<w:p>` count |
| --- | --- | --- |
| dasimulator-1.docx (Assets and Debts Statement, Original) | word/document.xml | 51 |
| dasimulator-3.docx (Assets and Debts Statement, Original) | word/document.xml | 51 |
| dasimulator-5.docx (Dissolution of Marriage Petition, Original) | word/document.xml | 51 |
| dasimulator-7.docx (Income and Expense Statement, Original) | word/document.xml | 51 |
| dasimulator-9.docx (Income and Expense Statement, Original) | word/document.xml | 51 |
| dasimulator-11.docx (Motion for Appointment of Next Friend) | word/document.xml | 3 |
| dasimulator-12.docx (Order for Appointment of Next Friend) | word/document.xml | 3 |

The other 7 published attachments (the Redacted variants and the Parenting
Plan pair) reported `structure` `"ok"`.

Additional observations:

- `docx read`/`python-docx` open every published attachment without error.
- Every authored template under the target package's
  `data/templates/` tree reports zero nested paragraphs before rendering.
- The redacted variants of the same documents, produced in the same run,
  report zero nested paragraphs.

## Expected behavior

No `<w:p>` element appears as a descendant of another `<w:p>` element in any
WordprocessingML part of a generated DOCX attachment, and strict structural
validation reports `"ok"` for every published DOCX.
