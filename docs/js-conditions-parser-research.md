# JS conditions parser research — issue #93

## Recommendation

Prefer **esprima2 AST + a tiny, explicitly allowlisted evaluator** over a handwritten JavaScript tokenizer/parser. This replaces syntax handling, not evaluation or field-binding policy. Arbitrary JavaScript, DOM access, function execution, and general coercion remain out of scope. Research only: no dependency, implementation, or issue changes were made.

**Invariant:** a condition must syntactically contain `val("literal field name")` referring to an actual rendered input on this screen. Without such a dependency it does not run, even for `true`. Namespace membership is not screen membership. Discover dependencies across the whole AST **before and independently of** short-circuit evaluation: `true || val("count")` and `false && val("count")` both contain a dependency. A rendered controller need not already have an answered value; an unrendered namespace variable is not a controller.

## AST API and limits

The [public API source](https://github.com/s0md3v/esprima2/blob/10e784b7ee903b81a430bc0f98f6fd92db8e700b/esprima/esprima.py) exposes `parseScript`, `parseModule`, and `tokenize`, not a standalone public expression parser. `parseScript` returns `Program.body`; require exactly one `ExpressionStatement`, then inspect its `expression`. Reject other statements and multiple expressions/statements rather than accepting whatever a script parser accepts. Use strict parsing (`tolerant=False`), no JSX, and reject unsupported AST nodes even in unreachable branches.

`val("count")` is `CallExpression(callee=Identifier(name="val"), arguments=[Literal(value="count")])`. Scan node objects or `.toDict()` iteratively. Only direct calls with exactly one ordinary string literal qualify; not member calls, computed arguments, template strings, or text in comments/string literals. Parsing builds syntax trees; it does **not** call `val`, evaluate conditions, or supply JS truthiness/equality. Python `eval`, `bool`, and `==` are not substitutes for the approved JS subset.

Resource safety is not automatic. The [recursive parser](https://github.com/s0md3v/esprima2/blob/10e784b7ee903b81a430bc0f98f6fd92db8e700b/esprima/parser.py) has no exposed time/node/depth budget; the [scanner](https://github.com/s0md3v/esprima2/blob/10e784b7ee903b81a430bc0f98f6fd92db8e700b/esprima/scanner.py) even compiles regex literals with Python `re` while parsing. Rejecting regex ASTs afterward cannot undo that cost. Apply a conservative source-length cap before parsing, catch syntax/recursion failures, and bound AST size/depth and evaluator operations afterward. These are mitigations, not a hard wall-clock/memory guarantee; a hard hostile-input guarantee would require separate isolation work, not silently expanding #93.

**CPython 3.10 probe:** downloaded the PyPI wheel to `/tmp`, verified SHA-256 `0596fae544e0a9d7a07b1243ee9e9016b568812c20f9a06cb8f85bbb7c2ef443`, extracted without installation, and imported via `PYTHONPATH` using `.venv-310/bin/python` (3.10.22). Both short-circuit examples retained literal `val` nodes; `true` had none; `val(name)` had a nonliteral argument; `val("x"); true` yielded two statements; malformed `val("x") ==` raised `esprima.Error`. Regex syntax parsed (not executed). 500 nested parentheses raised `RecursionError`. These are focused API probes, not full compatibility or security certification.

## Upstream no-trigger behavior

Source evidence supports the invariant, with an important fidelity caveat:

- Installed docassemble 1.9 lane `base/parse.py:4168–4195` builds `show_if_js` with `sign`, `mode`, expression, and `vars`; extraction uses regex for literal `val`, `getField`, and `daGetField`, not an AST. Thus an AST scanner is deliberately cleaner, but not byte-for-byte equivalent for spacing, escaped strings, comments, or Mako-generated calls. Preserve/check compiled trigger metadata when assessing browser fidelity; do not claim every AST-recognized call necessarily registers upstream.
- Pinned upstream [`app.js:5437–5635`](https://github.com/jhpyle/docassemble/blob/36d7bd4d27324a3cde2ea92ebd5afe074cdcfe2d/docassemble_webapp/docassemble/webapp/static/app/app.js#L5437) registers handlers only inside `jsInfo.vars` → matching rendered DOM elements. `eval(jsExpression)` is inside those handlers. No matching trigger means no evaluation, not “evaluate once with namespace values.”
- Installed `standardformatter.py:1339–1352` initializes mode 0 wrappers (`js show if` **and** `js hide if`) with `display: none`; mode 1 wrappers (`js enable if` **and** `js disable if`) have no such hiding style. With no triggers, source indicates both show/hide remain initially hidden, while enable/disable do not apply their condition and leave baseline input state unchanged. This is **source-based inference, not browser-tested across both supported runtime versions**. Other disabling/visibility rules can still apply. In particular, do not implement no-trigger as Boolean false followed by sign inversion: that would incorrectly reveal `js hide if`.

## Minimal adjusted plan

1. Replace only the planned handwritten syntax layer with a reviewed esprima2 version (6.0.0 baseline); keep a private parser/AST adapter. Preserve explicit unsupported/error diagnostics and bounded inputs.
2. Independently collect literal dependencies and intersect with canonical **rendered input** identities, including existing generic/index mappings—not `user_dict` keys. Keep “no trigger” separate from false, unsupported, and missing answer. Check compiled `vars` discrepancies rather than broadening upstream behavior accidentally.
3. Validate the entire AST against the already approved subset, then evaluate only literals, direct literal `val`, approved comparisons, `!`, `&&`, and `||`, with explicit primitive JS semantics and short-circuiting. Parser support for modern JS is not evaluator permission. Apply show/hide sign only after a triggered evaluation; do not expand #93 into enable/disable implementation.
4. Add source-named tests for constant true/false, namespace-only/absent controllers, rendered unanswered controllers, short-circuited calls, nonliteral/comment/member lookalikes, sign inversion/no-trigger hide, unsupported dead branches, syntax/size/depth failures, and #93 count swapping. Run fast tests and CPython 3.10; verify initial no-trigger browser states and compiled-trigger edge cases in both runtime lanes before claiming exact parity.

Compared with a handwritten parser, this removes substantial escaping, precedence, tokenization, and syntax-error maintenance, and reuses a proven sibling pattern. The evaluator, screen-value adapter, resource bounds, and no-trigger policy remain equally necessary. Confidence: **high** on package/LSP/API evidence and the recommendation; **medium** on exact cross-version browser-state parity until runtime probes are added.
